# SAP HANA: the engine rules the oracle rests on

Every rule below is something the provider's renderings or its reference semantics
(`semantics.py`) assume. The status column says where each comes from:

- **doc**: SAP's documentation, QRC 3/2026 (SQL Reference, JSON Document Store Guide,
  SPARQL Reference, Knowledge Graph Guide);
- **assumed**: the SQL standard / SPARQL 1.1, not stated by SAP for HANA;
- **probe Xn**: `ganda hana probe` checks it (`scripts/probe.py`);
- **probed 2026-10-09**: confirmed live against HANA Cloud 4.00.000.00 (`SYS.M_DATABASE.VERSION`
  = `4.00.000.00.1788859455`), the whole probe green (57/57) and the first campaigns run;
  **probed 2026-10-11 / 2026-10-12**: the graph facts, then the plan-steering, NOT, custom-key
  and inheritance facts, then the sixteen facts of the improvement plan (cross-type pivots,
  SQL constants, the set-operation form, isolation across connections, SQLScript blocks,
  GraphScript, the triple store's decimal AVG, the hinted collection query: 141 facts in
  all; the K facts re-run 2026-10-12 after a probe-script bug had kept them from running
  since the graph commit).

Engine defects found live, written up with repros under `issues-draft/`:
**H1** (an `xsd:double` is serialized to ~6 significant figures in SPARQL results though stored
exactly), **H2** (the Document Store crashes with an internal error on a correlated scalar
subquery whose inner query reads a collection through UNNEST), **H3** (SPARQL SUM / AVG
turn unbound over a group with an unbound value once the predicate has held a second datatype
anywhere in the store), **H4** (a SUM over collection views overflows on rows a JOIN
excludes), **H5** (`BETWEEN ? AND ?` over a collection field types its parameters BIGINT) and
**H6** (a legal FILTER / BIND over a variable bound nowhere is refused). The provider works around
H1-H3, H5 and H6 and withholds H4's shape.

When a probe fact fails, change the provider, not the probe: see `HANDOFF.md`, "When a
probe fact fails".

## The four data models

| Rule | Status |
|---|---|
| A campaign database is a SCHEMA (tables, collections, the graph data model's views and workspace) plus a NAMED GRAPH `<urn:ganda:g:<schema>>`. Graphs belong to the user, not to a schema. | doc |
| A query with no FROM / GRAPH reads every graph (HANA differs from SPARQL 1.1 here): every rdf text names its graph, `GRAPH <g> {...}` or `FROM <g>`. | doc |
| `CREATE GRAPH` / `DROP GRAPH` need auto-commit on; an `INSERT DATA` into a missing graph creates it. | doc |
| SPARQL updates join the SQL transaction (COMMIT / ROLLBACK cover both). | doc, probe K15, probed 2026-10-09 |
| `SYS.SPARQL_EXECUTE(text, headers, ?, ?)` through `callproc`; the response is OUT parameter 3; `Accept: application/sparql-results+json` gives SPARQL JSON results; an update answers nothing. | doc + langchain-hana source, probe K0/K1, probed 2026-10-09, probed 2026-10-09 |
| `SPARQL_TABLE('<one SELECT>')` answers one SQL column per variable, typed after the datatypes the variable's PREDICATE holds across the whole graph: one datatype gives a typed column (OPTIONAL or not), several give an NVARCHAR column -- a number as its digits, a boolean as `1` / `0` -- even for a variable bound in every row. A campaign's field predicates (`p:f1`) are shared by classes of different types, so every value projection carries its decode suffix (`?a AS ?a__int` / `__bool`, `STR(?a) AS ?a__float`) and the session re-types it; a COUNT stays an integer. A string over 5000 characters becomes NULL. | doc, probe K12/K13, probed 2026-10-09 (the typing rule: found live in campaign-20261009-095838, pinned by a scratch-graph probe) |
| **Isolation across connections**: a second connection sees none of a first one's uncommitted writes while its transaction is open -- column tables (INSERT / UPDATE / DELETE), a collection (its INSERT / UPDATE / DELETE), the triple store (INSERT DATA / DELETE-INSERT / DELETE WHERE inside the SQL transaction) and the graph workspace's dynamic cache through `OPENCYPHER_TABLE` -- and the committed state after the rollback; the first connection sees its own. The transaction door's peer check rests on it (`connection.HanaSession.execute`). | probe R24 / D26 / K27 / G37, probed 2026-10-12 |

## Values

| Rule | Status |
|---|---|
| BIGINT keeps the 64-bit range; DOUBLE keeps DBL_MAX; `-0.0` is stored as `+0.0` (the pools hold no `-0.0`). | doc, probe R1, probed 2026-10-09 |
| NVARCHAR holds at most 5000 characters; it compares in binary order (UTF-16 code units, CESU-8 storage), without padding (`'a' <> 'a '`); `''` is not NULL. | doc (length), assumed (order), probe R3/R4, probed 2026-10-09 |
| SPARQL compares strings by code point; on the Basic Multilingual Plane that is UTF-16 order, so the pools hold no astral code point. | assumed (SPARQL 1.1) |
| An integer is stored in the triple store as `xsd:long` (`xsd:integer` is not among the documented types), a double as `xsd:double`, a boolean as `xsd:boolean`. | doc, probe K1/K2, probed 2026-10-09 |
| **H1**: an `xsd:double` is stored exactly but SERIALIZED to ~6 significant figures in every SPARQL result format; `STR(?d)` carries the exact lexical form, printed `%.17g` -- so an integral double has neither point nor exponent (`STR` of 2^53 is `9007199254740992`, its term `9.0072e+15`). So the provider reads every rdf double through `STR(?v)` and parses it, whatever its lexical form looks like (`connection._rdf_records`/`_exact`, the `__float` projections of the case queries and of the write read-backs). | probed 2026-10-09, issues-draft/H1 (the `%.17g` form found live in campaign-20261009-095838: every seed holding 2^53 in a float field failed its state check) |
| The document store keeps a JSON integer as BIGINT and a number with a fraction or an exponent as DECIMAL (collections created since QRC 3/2024); it compares integer and number as one type; it never casts implicitly (a string `'10'` does not equal the number `10`). | doc, probe D1/D4/D5, probed 2026-10-09 |
| A field projected from an NVARCHAR collection reaches SQL as text: a number as its digits, a string unquoted, a boolean as `true` / `false`, an array as its JSON text, a JSON null as SQL NULL. | doc (text), assumed (the boolean's and the number's exact text), probe D2, probed 2026-10-09 |
| A parameter in a collection filter must be cast (`CAST(? AS BIGINT|NVARCHAR|DOUBLE|DECIMAL|BOOLEAN)`); a bare `= ?` is refused, and so is every marker of an `IN (?, ?)` list (the doc write's read-back expands its captured ids one cast each). A boolean is compared with `TO_JSON_BOOLEAN(TRUE)` in an NVARCHAR collection. | doc, probe D4/D5/D6, probed 2026-10-09 (the IN list: found live in campaign-20261009-095838) |
| A LIST is held as its canonical JSON text (`[1,2]`) plus its elements (a child table on rel, `i:` triples on rdf, the JSON array on doc). | the provider's design |
| **A cross-type numeric pivot** (`pivots.cross_type`: an INT field against a double `v ± 0.5`, a FLOAT field against an integer, both below 10^12 in magnitude) compares as Python compares an int with a float on every data model: SQL with the parameter typed by the PIVOT (`CAST(? AS DOUBLE)` against BIGINT; a bare `?` takes the column's type and truncates 1.5 to 1), the collection filter with `CAST(? AS DOUBLE)` / `CAST(? AS BIGINT)` (the store compares integer and number as one type, exactly even at 2^53 + 1), SPARQL by numeric promotion, openCypher with BOTH sides `TOFLOAT(...)` (`TOFLOAT(a.F) > TOFLOAT('0.5')`: the engine refuses a BIGINT attribute against a float and a DOUBLE attribute against an integer constant outright, `[4906] Type mismatch between bigint and float`; a bound double against a BIGINT attribute is silently truncated, as SQL's bare `?` is). The bound keeps every BIGINT→DOUBLE conversion harmless: SQL and SPARQL convert 2^63 - 1 to 2^63 against a double pivot of 2^63, where Python does not. | probe R21 / D24 / K24 / G36, probed 2026-10-12 |
| A constant written into a SQL text means the bound value (the `inline` position): a DOUBLE as an approximate numeric literal (`repr` with an exponent, `0.1E0`; the exact numeric literal `0.1` compared equal too on the boundary pool), BIGINT's two ends as digits, `N'...'` strings (a quote doubled, an astral code point, 5000 characters, a backslash), `TRUE` / `FALSE`. | probe R22, probed 2026-10-12 |

## Nulls and logic

| Rule | Status |
|---|---|
| An absent field and an explicit null are one null on every data model (`IS NULL` holds for both on doc). | doc (doc), assumed (rel: both NULL; rdf: no triple), probe D7, probed 2026-10-09 |
| SQL is three-valued; a record is kept only where the filter is TRUE. | assumed (SQL) |
| The rdf base renderings spell three-valued logic out with `BOUND` guards; the `native` variants rely on SPARQL's error propagation (`error && false` is false). **H6**: HANA refuses a FILTER (or BIND) naming a variable bound nowhere -- even `FILTER(!BOUND(?x))`, true for every solution per SPARQL 1.1 (§17, §18.2.1) -- while `COALESCE(?x, 1)` is accepted; so the native semi-join declares its never-bound `?ganda_unknown` with a never-matching OPTIONAL, after which every form is accepted and answers per the standard. | assumed (SPARQL 1.1), probe K5/K6, probed 2026-10-09 (the declaring OPTIONAL, found at probe K6), issues-draft/H6 |
| `FOR ANY ... SATISFIES ... END` is false (not unknown) over an absent array, so its negation holds; the doc filter never negates one anyway (`document.doc_pred` raises and the question is asked through the views). | assumed, probe D8, probed 2026-10-09 |
| SQL `IN (SELECT ...)` is rendered with `g IS NOT NULL` inside, so a semi-join is unknown only for a null field. | the provider's design |

## Query forms

| Rule | Status |
|---|---|
| `ORDER BY ... NULLS FIRST / NULLS LAST`, `LIMIT n OFFSET m` (an OFFSET only after a LIMIT: `LIMIT 2147483647 OFFSET m`). NULL sorts first ascending when no NULLS clause is given. | doc (syntax), assumed (default), probe R5/R6, probed 2026-10-09 |
| The document store orders `null < number < string < object < boolean < array`, so a collection ORDER BY puts nulls (and absent keys) first ascending, last descending, without a NULLS clause. | doc, probe D12, probed 2026-10-09 |
| AVG of BIGINT is `DECIMAL(25,6)` (documented): the exact quotient TRUNCATED to six places (`7 / 128` is `0.054687`, `-5479 / 29` is `-188.931034`; `semantics.mean`); SUM of BIGINT is exact below 2^63. The triple store's AVG over `xsd:long` (and `/` of two longs) is `double(SUM) / COUNT` instead (**B13**: a sum above 2^53 loses its low bits, a quotient keeps seventeen digits where SQL keeps six), so an rdf `avg` is compared only where the two agree -- a sum below 2^53 and a quotient exact in six places (`known_bugs`); the triple store's `xsd:decimal` is no way round it: `xsd:decimal(SUM(?w)) / COUNT(?w)` and a FLOOR truncation of it print a double's digits (`-188.93103448275863`, `0.054686999999999999`), so SQL's DECIMAL(25,6) value is unreachable in SPARQL (probe K25). MEDIAN in SQL answers in the argument's type: over integers the mean of the two middle values ROUNDED to an integer, half away from zero (`{1,2}` 2, `{1,10}` 6, `{-3,-2}` -3; DECIMAL and DOUBLE keep the fraction), so the provider renders the statistical median as `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY f)` (in a scalar subquery, for the NULL row over no value). HANA's SPARQL MEDIAN interpolates but is refused without a GROUP BY, so the rdf rendering groups on a bound constant. | doc (AVG), probed 2026-10-12 (R20, K23: found live, the 12-hour campaign), assumed (SUM), probed 2026-10-09 (MEDIAN forms, found live), probe R7/R8/R9/K16 |
| **H3**: `SUM` / `AVG` skip an unbound value only while the predicate IRI has held one datatype; once it has held a second one ANYWHERE in the store (another class, another graph, a graph since dropped -- a campaign's `p:f1` always has), a group with an unbound value in it answers UNBOUND (`MAX` and `COUNT` still skip it). So a select `sum` / `avg` binds its value as a required triple (a null is skipped by the aggregate anyway), a `group` sum adds `COALESCE(?a, 0)`, and a traversal sum needs neither (a start's values are all bound, or it has one unbound row). | probed 2026-10-09, probe K20 (found live in campaign-20261009-165805: 9 sum / avg mismatches) |
| SPARQL aggregates skip an unbound value; `SUM` / `AVG` of nothing are 0 in SPARQL, `MAX` of nothing is unbound; the renderings guard a sum as `IF(COUNT(?w) > 0, SUM(?w), MAX(?w))`, all aggregates, because a grouped SELECT refuses a bare variable outside an aggregate (`?ganda_unknown` there: `[129] Non GROUP BY variable in SELECT`, as SPARQL 1.1 11.4 says); `COUNT` over nothing is 0. | assumed (SPARQL 1.1), probe K7/K8, probed 2026-10-09 (the grouped-SELECT refusal: found live in campaign-20261009-095838) |
| A grouped SPARQL query over no solution answers no row; the renderings add `HAVING (COUNT(*) > 0)` (a no-op by the standard) because rdflib answers one empty group. | assumed, probe K9, probed 2026-10-09 |
| SPARQL property paths `?`, `/`, `^`, `|` (no `{n,m}`); MINUS; FILTER [NOT] EXISTS; subqueries; IF; STRDT. | doc, probe K10/K11/K14, probed 2026-10-09 |
| An `EXISTS` inside `GRAPH` in an update's WHERE reads the named graph (the rdf write marks its records with one). rdflib does not, so the offline stand-in selects the marks with a query. | assumed, probe K19, probed 2026-10-09 |
| The collection SELECT filter: a path compared with a cast value, `IS [NOT] NULL`, `LIKE`, `FOR ANY`, AND / OR, parentheses. `IN` is rendered as ORs, `BETWEEN` as two comparisons, `NOT` pushed down to the leaves. A LIKE right-hand side is a constant string literal (or `TO_NVARCHAR` / `UPPER` / `LOWER` of one) or the documented `CAST(? AS NVARCHAR)` -- the same cast WITH a length is refused; the provider inlines the pattern. | doc (grammar, `CAST(? AS NVARCHAR)`), assumed (parentheses, NOT LIKE), probed 2026-10-10 (findings B4) |
| The collection query's `MAX` / `MIN` take numbers only: over a string field they fail with an error code 129 ("max supports only numeric values"), a refusal rather than a crash; the same aggregate over the views (SQL over `TO_NVARCHAR`) and the collection's `ORDER BY ... LIMIT 1` answer. So a string `max` / `min` (an `agg` or a `group` value) is asked through the views (`select._string_extremum`). | probed 2026-10-09 (found live, seed 1 of the verification run) |
| **H5**: over a collection field read through SQL (a view), `f BETWEEN ? AND ?` types its PARAMETERS BIGINT and fails on a string (`[-10427]`), while `f >= ? AND f <= ?` answers; so the doc views type every string field `TO_NVARCHAR` (`document.sql_cast`). | probed 2026-10-10, issues-draft/H5 (was findings B9) |
| The collection UPDATE / DELETE filter is narrower: comparisons, BETWEEN, IS NULL, AND / OR. A doc write whose filter is outside it chooses its records with a SELECT first and writes them by id (`concrete_syntax/write.py`, `_doc`). UPDATE takes only constant SET expressions (no `$."f" = $."f" + c`): an arithmetic write reads the value, shifts it and writes a constant back, per row. | doc, probed 2026-10-09 (constant-only SET, found at probe D13) |
| `UPDATE c SET $."f" = PARSE_JSON(?) [, ...] WHERE ...` and `UPDATE c UNSET $."g" WHERE ...` combine as `SET ..., UNSET ...` -- WITH a comma, as the docs' example writes it (without one, a syntax error); the provider issues them as two statements; `SET c.$ = PARSE_JSON(?)` replaces a document; `UPDATE` and `DELETE` answer their row count. | doc (forms), probed 2026-10-10 (findings B5), probe D13/D14/D15 |
| `UNNEST $."arr" AS "x"` (chained: `UNNEST "l"."arr" AS "y"`) skips an absent array; an element's field is `"l"."f"`. A WITH view over collections joins with SQL, but the BOOLEAN cast (`CASE ... THEN TRUE`) must live one CTE removed from any collection read -- a main view is a `raw_v_X` CTE (collection text) plus a `v_X` CTE (the casts over `raw_v_X`) -- because the Document Store refuses a BOOLEAN constant in a query that reads a collection. | doc, probe D9/D10/D16, probed 2026-10-09 (the two-CTE split, found at probe D16) |
| The Document Store refuses an UNNEST-based view NESTED inside a subquery (`IN (...)`, a correlated EXISTS over a double-UNNEST edge-element view): "unsupported form of subquery with UNNEST". So the doc path `frontier` form is dropped and the doc view variants withhold an edge LIST-membership (`concrete_syntax/path.py`, `select._views_ask`); a node's single-UNNEST element view inside EXISTS is accepted in a select as a positive conjunct, but NOT under OR or NOT, not inside a semi-join's subquery, and not in a query that also joins the UNNEST edge views: so the views ask a LIST membership only as a positive conjunct (`document.views_ask`, for selects and writes) and a doc traversal withholds every LIST membership (`traversal.applicable`). | probed 2026-10-09, found live (the traversal case: campaign-20261009-095838) |
| **H2**: the Document Store CRASHES (internal error, code 3) on a correlated scalar subquery whose inner reads a collection through UNNEST; the LEFT JOIN + GROUP BY rewrite answers. So the doc traversal `scalar` syntax is withheld for aggregates and reach counts (`concrete_syntax/traversal.py`, `applicable`); the `join` syntax covers them. A CONTAINSALL over the doc views is the same shape (`(SELECT COUNT(DISTINCT x.v) FROM v_t__l x WHERE x.owner = t.id ...) = n`) and crashes in a plain select too, so the views ask it as one EXISTS per element (`predicate.sql`, `Names.count_membership`). | probed 2026-10-09, issues-draft/H2 (the CONTAINSALL form: campaign-20261009-095838) |
| **H4**: SQL over the collection views adds up the values of rows a JOIN excludes: a SUM over a join of an UNNEST link view (read whole: its id, ends and value, the value cast in a CTE of its own) fails with `[314] numeric overflow` when the excluded links' values exceed BIGINT together, though the join matches no row (`SUM(TO_DECIMAL(...))`, or the value column read alone, answers NULL). A doc traversal sum whose projected column holds an absolute total of 2^62 or more is withheld (`known_bugs.py`). | probed 2026-10-09, issues-draft/H4_repro.py (found live in campaign-20261009-165805: 4 traversal sums) |
| Column tables: `UPSERT t (cols) VALUES (...) WHERE id = ?`; `MERGE INTO t USING (...) s ON ... WHEN MATCHED THEN UPDATE SET ...`; `MERGE DELTA OF t`; `CREATE [UNIQUE] INDEX` (an INVERTED VALUE index; INVERTED HASH / INDIVIDUAL exist for composite UNIQUE constraints only, so the provider draws neither); a UNIQUE index admits several NULLs; `PARTITION BY HASH (id) PARTITIONS n`. `START` is a reserved word, so the traversal renderings alias the start column `strt`, not `start`. | doc, probe R12/R13/R14, probed 2026-10-09 (START reserved, found live) |
| **The set-operation form** (`tlp`): the records a filter keeps are every record `EXCEPT` those where it is false `EXCEPT` those where it is unknown -- `(CASE WHEN p THEN 1 WHEN NOT (p) THEN 0 END) IS NULL` -- for comparisons, LIKE under OR, IN, NOT IN, a NOT over EXISTS, IS NULL, counted as a derived table too; on SQL over column tables and over the collection views alike (two collection queries themselves take no EXCEPT: `[7] feature not supported`, as UNION ALL, D23). In SPARQL the partition is `MINUS`, with the filter carried as `BIND ((p) AS ?t) FILTER (?t)` (an error leaves `?t` unbound, which the FILTER drops) and the unknown partition `COALESCE(IF(p, 1, 0), 2) = 2`: the BIND is required, because a plain `FILTER` over `COALESCE` of an OPTIONAL variable keeps or drops the wrong solutions (`FILTER (COALESCE(IF(?i > 1, 1, 0), 2) = 2)` is true for every one, so the plain partition removes everything), though the same expression is right through BIND and as a selected value -- an engine defect (A10, `findings/`, narrowed live 2026-10-13). | probe R23 / D25 / K26, probed 2026-10-12 |
| **SQLScript anonymous blocks** (the `block` positions): `DO (IN sv_p BIGINT => ?) BEGIN ... END` answers a result set to the client; every statement shape (a CTE, a derived table with a LEFT JOIN and a correlated scalar subquery, GROUP BY / ORDER BY / LIMIT, a semi-join with EXISTS, DISTINCT with NOT IN, PERCENTILE_CONT, a view over a collection, OPENCYPHER_TABLE, SPARQL_TABLE, the collection query itself) answers its plain rows as the block's own SELECT, through a table variable (`sv_t = SELECT ...; SELECT * FROM :sv_t;`), and with `WITH HINT (NO_INLINE)` on the assignment; a hinted inner SELECT is accepted. The header types the binds; the body's `:sv_*` are SQLScript variables that `connection.positional` leaves alone. | probe P20, probed 2026-10-12 |

## The graph data model (the Property Graph Engine)

The workspace is `gw`, one per campaign schema, over one VIEW per node table and junction
table (`gv_<t>`: the keys and a base-class field under their names, an own field
`<t>_<f>`), labelled by the logical names (`LABEL 'n1'`); openCypher reaches it through
SQL's `OPENCYPHER_TABLE` (`dialect.opencypher_table`, `concrete_syntax/graph.py`). Each
row names the probe fact behind it (`ganda hana probe G`, run 2026-10-11 against HANA
Cloud 4.00.000.00: 32 facts); where the engine departs from the SAP Property Graph Engine
Reference (QRC 2/2026) the row says so. A rule the probe overturns changes the switch of
the same name in `concrete_syntax/graph.py` (and the offline translator's,
`tests/hana/opencypher_sqlite.py`), never the probe.

| Rule | Status |
|---|---|
| A workspace wants ONE type per attribute name across its vertex tables (and across its edge tables); a class's own `f1` is drawn per class, so the workspace reads the tables through views that qualify an own field `<table>_<field>`. A graph table may be a table, a view or a synonym; a TABLE-backed key needs NOT NULL + UNIQUE and NOT NULL endpoints, a view skips the check (a view over a HASH-partitioned table whose key is NOT NULL without a PRIMARY KEY is a valid graph table). With several vertex tables every edge table says `REFERENCES`; `(a:n1)` matches `LABEL 'n1'`; `SYS.GRAPH_WORKSPACES.IS_VALID` is the text `'TRUE'`. | doc, probe G0/G0b/G17, probed 2026-10-11 |
| Over a workspace with ONE vertex table and ONE edge table, a MATCH naming the VERTEX label (`(a:v)`, declared or the default table name; tables or views) fails with `[260] invalid column name: a.CYPHER$TABLE$LABEL` (an internal column leaking); the edge label, `LABEL(a)` in RETURN, the unlabelled pattern, and any workspace with a second vertex table OR a second edge table answer. A campaign's workspace always has two or more edge tables, so the provider never meets it. Filed as `findings/A7-opencypher-homogeneous-labelled-workspace/`. | probe G27, probed 2026-10-11; the matrix repro 2026-10-12 |
| `OPENCYPHER_TABLE(GRAPH WORKSPACE gw QUERY '<cypher>' [PARAMETERS ('k' = ?, ...)])`: the query is a SQL string LITERAL (its quotes doubled), the result a table typed by the workspace's columns (BIGINT, DOUBLE, NVARCHAR, BOOLEAN; COUNT a BIGINT) named by the RETURN aliases -- unlike SPARQL_TABLE, so a projection needs no decode suffix but a LIST's `__JSON`. The table function composes in SQL: a CTE, a derived table, a LEFT JOIN, a correlated scalar subquery, IN / NOT IN (the views family and the native wrappers). | doc, probe G1/G1b/G19/G23, probed 2026-10-11 |
| A `$name` is bound by name from the PARAMETERS clause, BARE only (`:name`, typed by the engine, exact above 2^53): a CAST there is refused (`[7] feature not supported: OPENCYPHER_TABLE parameter initialization with values`), so `graph.TYPED_PARAMS` stays off. `connection.positional` skips the quoted query, so `(a:n1)`, `[*1..2]` and `$p` inside it are not binds. | probe G2/G2b, probed 2026-10-11 |
| **A9**: a statement holding TWO `OPENCYPHER_TABLE` calls types the second call's bare parameters in the wrong order when they mix a string and a number (a string `?` declared BIGINT / DOUBLE: `[-10427]` from the client; a double next to a BIGINT converts silently to wrong rows); each call alone is typed by the attributes. So one call binds parameters of ONE type: a DOUBLE pivot is bound, every other pivot -- an integer (exact to 2^63 - 1), a string (`\'`, `\\`; a control character has no constant: the views ask it), a LIST's JSON text -- is a constant in the query (`graph.cypher_filter`, `graph.literal`). Filed as `findings/A9-opencypher-two-calls-parameter-types/`. | probe G30/G32/G34, probed 2026-10-12 (found live, the 12-hour campaign) |
| **A8**: a DOUBLE constant written in the query text is parsed to about fifteen significant digits (one and two ulps off a stored value compare `=` to it), while a bound DOUBLE parameter and `TOFLOAT` of a string constant compare exactly. So a double is never a constant in a cypher text (the `literal` variant that inlined constants is gone). Filed as `findings/A8-opencypher-double-constant-loses-digits/`. | probe G31, probed 2026-10-12 (found live, the 12-hour campaign) |
| A BOOLEAN attribute is refused inside `COUNT(...)` and in a comparison of two attributes (`[4906]`, B14), and answers as a group key or projected: a native text counts no BOOLEAN field and correlates no self-join on one (`select._cypher_asks`). | probe G33, probed 2026-10-12 |
| Attribute names and RETURN aliases are case-sensitive; the unquoted DDL leaves uppercase names in the catalog, so the cypher spells `a.ID`, `a.N1_F1`, `AS V` (`a.id` is "Attribute not found"; `AS id` is a column SQL reaches only quoted). | doc, probe G16, probed 2026-10-11 |
| **A heterogeneous workspace -- every campaign's -- takes ONE MATCH clause** (a second: `[4906] For heterogeneous graphs only one match clause is allowed`; the docs' five-clause limit is for homogeneous ones), of comma-separated patterns, each ONE edge (a chained `(a)-[e1]->(b)-[e2]->(c)` is a syntax error) or one variable-length path. No incoming arrow (`<-[`): a hop in is the pattern reversed. No OPTIONAL MATCH, UNION, WITH, UNWIND, IN list, boolean constant. | probe G8/G8b/G9/G22, probed 2026-10-11 (departs from the docs) |

## Plan steering (`concrete_syntax/hints.py`)

A `WITH HINT (...)` clause closes a SELECT and steers it to another execution engine or
optimizer mode without changing what it means (SQL Reference, "HINT Details", QRC
3/2026); the provider asks every SQL text once more under one of sixteen profiles
(`hints.PROFILES`: `nohex`, `hex`, `esx`, `olap`, `join_engine`, `row_ops`, `cs_ops`, `rule_based`,
`minimal`, `no_rewrite`, `disjunction_split`, `hex_disk`, `nested_loop`, `hash_join`,
`no_index`, `serial`), one per question, as the variants `rel:<profile>`,
`doc:nest+<profile>`, `graph:<profile>`, `rdf:table_fn+<profile>`, `rel:hint_<profile>`.
A hinted twin answering differently from its plain statement is an engine defect with
no cross-model confound.

| Rule | Status |
|---|---|
| The hint clause is the last clause of a SELECT, after LIMIT / OFFSET, and closes a `WITH ... SELECT` query, a statement over a derived table with a LEFT JOIN and a correlated scalar subquery, one reading `OPENCYPHER_TABLE` or `SPARQL_TABLE`, and a SQL view over a collection alike; `THROW_ERROR` blocks the statement (`[256] statement execution blocked by the THROW_ERROR hint`), and an unknown hint name is an error, not ignored (`[468] hint error: invalid hint`). | doc, probe P0, probed 2026-10-12 |
| Every profile is accepted on every one of those shapes and answers the plain statement's rows. A profile the engine refuses on some shape would be dropped from `hints.PROFILES`, not worked around. | probe P1-P16, probed 2026-10-12 (fourteen profiles; `hex` and `esx` accepted on every shape the same day, their row comparison the next run) |
| `USE_HEX_PLAN` and `USE_ESX_PLAN` are accepted on every shape (the first run recorded them), so they are the profiles `hex` and `esx`; `IGNORE_PLAN_CACHE` was accepted on every shape as an observation and is the profile `plan_cache` (its row comparison: probe P17, the next live run). Beside it the `again` position runs the rel base text a second time, through the cached plan. | probed 2026-10-12, probe P17 |
| The collection query under every profile answers its plain rows (a filter with LIKE, an ordering with LIMIT, a count, a GROUP BY): the hinted `doc:<profile>` variant rides the collection query where the store asks the question, the views otherwise. | probe D27, probed 2026-10-12 |
